# DataVortex — Data Quality Report
**Stage 2 · Data Rescue.** _Turning UPI Data Chaos into Fraud Intelligence._

Generated by `scripts/run_pipeline.py`. Every figure below is computed at run time — nothing in this document is hardcoded.

```
RAW -> duplicate rescue -> ID normalization -> amount normalization
    -> timestamp normalization -> status normalization -> MCC normalization
    -> KYC repair -> chargeback normalization -> identity resolution
    -> relationship validation -> CLEAN
```

**Governing principle: no row is ever silently deleted.** Records that cannot be repaired are retained with a quality flag and a written reason. The only rows removed anywhere in this pipeline are byte-identical duplicates, and only after proving they are identical on every column.

### Is the residual mismatch a cleaning failure?

Tested against the null hypothesis of independent random draws over the observed ID space:

| pair | id_space | left_distinct | right_distinct | expected_overlap | observed_overlap | sd | z_score | verdict |
|---|---|---|---|---|---|---|---|---|
| tx.user x kyc.user | 90,000 | 17,878 | 28,920 | 5,745.00 | 5,799 | 62.40 | 0.87 | consistent with chance |
| tx.merchant x mer.merchant | 9,000 | 8,051 | 4,343 | 3,885.00 | 3,893 | 44.80 | 0.18 | consistent with chance |
| cb.txn x tx.txn | 99,999,999 | 2,567 | 20,000 | 1.00 | 2,451 | 0.70 | 3,420.33 | genuine relationship |

A z-score near zero means the overlap is exactly what chance would produce, so **no amount of normalization can raise it** — the source files drew their user and merchant IDs independently. The chargeback-to-transaction link, by contrast, is overwhelming, which is why it is the only relationship used for attribution.

**Unmatched rows are retained, not dropped.** They point at each dimension's `UNKNOWN` member so that every metric still reconciles to the full transaction count:

- transactions with an unresolved user: **13,522** (67.61%)
- transactions with an unresolved merchant: **10,369** (51.84%)
- chargebacks not linked to any transaction: **193** (6.89%)

### Where the KYC and merchant rows went

The negative differences above are **resolution, not deletion**. Every source row is still accounted for:

| Source | Raw rows | Exact duplicates collapsed | Rows after dedup | Dimension survivors | Non-survivors kept in bridge | Accounted for | Unaccounted |
|---|---|---|---|---|---|---|---|
| KYC | 36,400 | 278 | 36,122 | 28,920 | 7,202 | 36,122 | 0 |
| Merchants | 6,210 | 12 | 6,198 | 4,343 | 1,855 | 6,198 | 0 |

A dimension holds one row per entity so that joins cannot fan out. The rows it does not carry are the non-survivor candidates, and all of them live in `BRIDGE_IDENTITY_COLLISION` — nothing is discarded, and every set-aside record is inspectable.
